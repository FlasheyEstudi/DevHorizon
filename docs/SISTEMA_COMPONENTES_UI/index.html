ArtesaNica · Sistema de diseño

Sistema de Componentes de UI

Biblioteca de elementos reutilizables para el desarrollo de la plataforma: encabezados y navegación, botones, tarjetas, formularios y estados de feedback. Cada componente usa exclusivamente los tokens de color, tipografía, radios y sombras definidos en DESIGN.md y declarados en src/styles/global.css (Tailwind CSS v4), por lo que se comporta igual en modo claro y oscuro.

  • Tokens: Terracota #B85536 · Azul Añil #285375 · Ocre #E2A349
  • Tipografía: Poppins
  • Contraste: WCAG 2.1 AA/AAA
  • Sin dependencias externas: HTML + CSS

01 Cómo usar esta guía

Cada bloque muestra el componente renderizado y, debajo, el marcado recomendado. Los ejemplos de código reproducen las clases reales que ya se usan en el proyecto, de modo que se puedan copiar directamente en un componente Astro/React.

Cinco reglas obligatorias

  1. Solo tokens semánticos. bg-primary, text-texto, border-borde, bg-blanco… Nunca colores sueltos (bg-[#B85536], text-gray-900, bg-white).
  2. Un color por intención. Terracota = acción principal; Azul Añil = contexto institucional/navegación; Ocre = acento y calificación; verde/rojo = solo estados de éxito y error.
  3. Todo componente debe verse bien en claro y oscuro. Si el bloque no aparece también en la sección 08, está incompleto.
  4. Estados obligatorios. Todo elemento interactivo define hover, focus-visible, disabled y —si aplica— loading y error.
  5. Accesibilidad mínima. Foco visible con anillo de 2 px ring-primary, texto de 4.5:1, áreas táctiles ≥ 40 px y aria-* cuando el estado no es visualmente evidente.
Nota sobre Tailwind. El proyecto usa Tailwind CSS v4: en src/styles/global.css el bloque @theme declara variables --color-*, --shadow-* y --font-*, y Tailwind genera automáticamente las utilidades (bg-primary, shadow-card, …). El modo oscuro se activa con la clase .dark en <html> (@custom-variant dark), y cada token cambia de valor sin tocar el marcado.

Anatomía de una card: media (imagen o tile, relación 1:1 o 16:9) → metadatos (origen + valoración) → título (máximo 2 líneas) → pie (precio y acción, separados con border-t). Las cards de una misma fila igualan altura y alinean el pie al fondo (flex flex-col + mt-auto).

Accesibilidad de formularios: una <label for> por control (nunca placeholder como etiqueta); autocomplete correcto (email, current-password, one-time-code); ayudas y errores enlazados con aria-describedby; estado inválido con aria-invalid; el resumen de errores usa role="alert" y recibe el foco tras un envío fallido; el botón de envío muestra el progreso y se inhabilita (aria-busy) para evitar dobles envíos.

9.2 Checklist antes de dar por terminado un componente

  1. Usa solo tokens semánticos (sin colores ni tamaños hardcodeados).
  2. Define hover, focus-visible, disabled y, si aplica, loading y error.
  3. Se ve correcto en claro y oscuro (y en móvil: 360 px de ancho mínimo).
  4. Áreas táctiles de 40–44 px y contraste ≥ 4.5:1 en textos.
  5. Etiquetas y estados expuestos con aria-*; iconos decorativos con aria-hidden.
  6. Comportamiento consistente con un componente equivalente ya existente (no duplicar).
  7. Textos en los tres idiomas del proyecto (ES/EN/MIQ) desde el diccionario, sin cadenas sueltas.

9.3 Reglas de mantenibilidad

  1. Prohibido usar clases de color no registradas (bg-emerald-500, bg-white, text-gray-900) salvo estados universales de éxito/error.
  2. Preferir siempre bg-primary, bg-secondary, text-accent-amber, bg-blanco, bg-fondo, text-texto, text-texto-secundario, border-borde.
  3. Si hace falta un valor nuevo, se añade como token en src/styles/global.css (claro y oscuro) y se documenta en DESIGN.md.
  4. Reutilizar antes de crear: revisar esta biblioteca y los componentes existentes.
  5. Validación visual continua: alternar el tema en cada vista afectada (astro dev).
